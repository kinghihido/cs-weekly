一个网址，从按下回车到看见页面

你在地址栏敲下几个字母，回车。屏幕白了一下，然后页面出现了 —— 你大概觉得是「打开了一个文件」。 实际上在你看不见的那 0.4 秒里，你的电脑跨越几千公里，和五六台机器来回问了十几句话： 这个名字是谁、你在不在、我们怎么加密、我要的那张纸给我、纸上还缺十张图。 这期把这 0.4 秒拆成五段，让你以后骂「这网站真慢」的时候，能骂到点子上。

先把那 0.4 秒摊开

这件事最容易被误解的地方是：以为「网站」是存在某个地方的一个文件夹，打开网址就是进去把文件取回来。

前半句对。你取回来的其实只有一张「施工图」（HTML），里面写着：这里放个标题、 那里放张图、这个按钮点了要变蓝。油漆、瓷砖、家具（样式表、脚本、图片）是浏览器看完图纸之后， 又跑了好几趟分别取回来的。

所以「网页慢」经常不是那张图纸慢，而是后面那十几趟慢。而这一整条路上，一共有五个关键站点：

01DNS名字 → 地址
02握手TCP + TLS
03HTTP点单与上菜
04CDN别从国外搬
05渲染把图纸变成画面

先记住一句贯穿全篇的话，后面的五节都在解释它：

本期的唯一核心句

慢的大头往往不是「数据有多少」，而是「要来回几次」。 一次往返 20 毫秒是光纤的常态，一次往返 200 毫秒是跨洲的常态 —— 而这条路上，光握手就要来回好几次。

这期讲完，下面这些问题你都会有确定的答案：

  • 为什么改了域名解析要等几小时才生效？
  • 为什么「海外服务器」不管配置多高，打开都慢半拍？
  • 为什么第一次打开慢、刷新就飞快？
  • 看到 502 和 404，哪个该找对方、哪个该改自己？
  • 页面白屏好几秒，到底是网慢、服务器慢，还是浏览器在忙？
你不是在「打开一个文件」，你是在发起一场跨越半个地球、来回十几次的对话。
01

第一站：DNS，把名字翻译成地址

kinghihido.github.io 这个名字，机器完全看不懂。机器只认 IP 地址，比如 185.199.108.153。 DNS（域名系统）就是那本电话簿：你报名字，它给号码。

为什么不用号码直接上网？因为号码会变，名字不会。GitHub 明天把服务器搬到另一个机房，IP 变了， 但 github.io 这个名字不用变。名字是给人用的稳定入口，IP 是给机器用的临时坐标 —— 这就是域名存在的全部理由。

查一次名字，可能要问四五个人

DNS 不是一个中央大数据库，而是一层一层的「我不知道，但我知道该问谁」。 点下面的按钮，看一次完整的查询是怎么跑完的：

DNS · 一次解析的六层问路
点上面的按钮开始 本次解析耗时 — ms

「再访问一次」按的是同一个按钮，但你会发现它一层都没问 —— 这就是缓存。

第一次要跑一整圈，第二次是 0 毫秒。这个差别，就是后面所有「快」的来源： 缓存不是让事情变快，是让事情不用发生。

三个天天遇到、但很少人想明白的现象

① 为什么改了 DNS 解析，要等几小时甚至一天才生效？
因为路上每一层都缓存了旧答案。而「这个答案可以记多久」是域名主人自己设的，叫 TTL （上面演示里那句「可以记 300 秒」）。你改了记录，但全世界几十万台缓存服务器手里的旧答案还没过期。 所谓「DNS 生效慢」，本质是在等别人手里的缓存过期。所以正经的迁移流程是：先把 TTL 调小，等一天， 再改记录 —— 这样全世界只需要等几分钟。

② 为什么「网站打不开」有时候换个网络就好了？
如果名字查不到，浏览器连门都找不到，提示通常是「找不到服务器 / DNS 解析失败」。 这时候开手机热点试一下：如果立刻能开，问题就锁定在解析这一层（本地 DNS 缓存、hosts 文件、或者你连的那个 DNS 恰好抽风）， 跟网站本身一点关系都没有。

③ 一个域名不等于一台服务器。
baidu.com 背后是成千台机器，DNS 每次可能给你不同的 IP（叫负载均衡）； 反过来，一台服务器上也可能住着几百个网站（叫虚拟主机）。 所以「同一个 IP 上有几万个网站」是正常的，不是有人蹭你的机器。

顺手一个实用技巧

在能开机的电脑上，hosts 文件是 DNS 的最前面一站 —— 你可以手动把某个域名写死到某个 IP， 它优先级高于所有 DNS 服务器。这就是「本地测试」「屏蔽某个网站」最土也最有效的办法。 Windows 在 C:\Windows\System32\drivers\etc\hosts，Mac 在 /etc/hosts。

02

第二站：握手，先建一条路，再上一把锁

拿到 IP 之后，浏览器还不能直接喊话。网络是不可靠的：包会丢、会乱序、会重复。 TCP 在不可靠的底子上做出一根「看起来可靠」的管子，第一件事是三次握手：

# 三次握手 —— 代价是一个「来回」，不是三次传输 你 → 服务器 SYN （在吗？我想连你） 服务器 → 你 SYN+ACK （在，我听到你了，你听得到我吗？） 你 → 服务器 ACK （听得到，开始吧） # 一次 RTT 有多长 家里光纤 / Wi-Fi 10 ~ 30 ms 4G / 5G 30 ~ 60 ms 卫星上网 600 ms 以上

连接通了，还不算安全 —— 中间任何一个路由器都能看见你在传什么。所以 HTTPS 要在管子里再套一层加密， 这叫 TLS 握手：验证对方证书是不是真的、协商出一把只有双方知道的钥匙。 好消息是 TLS 1.3 把这一步压到了一个来回（老版本要两个）。

为什么工程师对「几个来回」这么抠

算一次就懂了：一个页面如果对 30 个不同域名各建立一次连接，每次 3 个来回， 在卫星网络上就是 30 × 3 × 600 毫秒 ≈ 54 秒。这不是夸张，这是很多老网站在偏远地区 真的打不开的原因。

反过来，一个 1 KB 的请求和一个 1 MB 的请求，在 100 Mbps 宽带上传输时间只差 80 毫秒； 但每多一次跨洲往返就是 200 毫秒起。所以优化的方向经常不是「减少数据」，而是「减少来回」。 HTTP/2 把多个请求塞进一条连接、HTTP/3 连握手都省了、TLS 1.3 把两次往返压成一次 —— 全是在干这件事。

顺手算一个物理极限

光在光纤里的速度大约是 20 万公里/秒（不是真空的 30 万，玻璃里会慢三分之一）。 一个来回 20 毫秒，意味着服务器离你大约 2000 公里。 北京到上海约 1200 公里；北京到洛杉矶约 10000 公里，单程 50 毫秒，一个来回 100 毫秒。

所以「海外服务器慢」不是配置问题

打开一个美国网站，不管它服务器多强，都至少比国内站慢 100 毫秒 —— 因为数据要跨太平洋跑一趟再跑回来。这不是优化能解决的，这是光速。 下一节讲的 CDN，就是人类对付光速的唯一办法。

03

第三站：HTTP，一张递进去的纸条

路修好了、锁上好了，浏览器终于可以说话。它说的话非常朴素，就是一张纸条：

# 请求（你递进去的纸条） GET /index.html HTTP/1.1 ← 我要什么（方法 + 路径 + 版本） Host: kinghihido.github.io ← 我要找哪一家（同一 IP 上可能住着几百家） User-Agent: Chrome / Windows ← 我是谁（顺便让网站决定给你哪个版本） Accept-Encoding: gzip, br ← 我能解压，你压缩了再发，省流量 Cookie: session=abc123 ← 上次你给我那张小纸条，我还带着 # 响应（它递回来的纸条 + 包裹） HTTP/1.1 200 OK ← 状态码：办成了 Content-Type: text/html ← 包裹里是什么 Cache-Control: max-age=600 ← 这个可以缓存 10 分钟 ↓ 空一行，然后是真正的 HTML

状态码：三秒看懂

不用背几十个，记住「谁的问题」就够了：

开头谁的问题常见成员
2xx 成功都没问题200 正常；204 成功但没内容
3xx 搬家你去别处301 永久搬走；302 临时搬走；304 你手里的没过期，直接用
4xx 你的问题请求不对401 没登录；403 没权限；404 没这个页面；429 请求太快被限流
5xx 它的问题服务器出事500 代码炸了；502 上游没响应；503 太忙；504 上游超时

4 开头是你敲错了或者没权限，5 开头是它自己出事了。 看到 502 / 504 就别再刷新了 —— 那是对方的后端在崩，刷新一百次也一样，等十分钟通常自己好。

Cookie：为什么关掉浏览器再打开，还是登录状态

HTTP 本身是失忆的：每个请求都是独立的，服务器不记得上一个请求是谁发的。 所以登录成功后，服务器在响应里塞一句 Set-Cookie: session=abc123，浏览器存下来， 之后每次请求自动带上。

一句话说透

「登录状态」本质上就是一张每次都要出示的通行证。 它不在服务器脑子里，而在你浏览器的一个小文件里 —— 所以清掉 Cookie，你就掉登录了； 所以别人拷走你的 Cookie，他就变成了你（这也是为什么公共电脑上一定要退出登录）。

顺带解释两个小现象：

  • Cookie 为什么不能存太多？因为每个请求都要带上它。多几百字节，乘以几十个请求就不是小数。
  • 为什么图片、CSS 常放在另一个域名下？那样就不用带 Cookie —— 这些静态文件根本不需要知道你是谁。

第四站：CDN，人类对付光速的唯一办法

假设你的服务器在硅谷，用户在北京。就算服务器是全世界最快的，也没用：数据得跨太平洋， 一个来回 100 毫秒，每次握手、每个请求都要走这一趟。

CDN（内容分发网络）解决的是「距离」问题，不是「速度」问题。 它在全世界放几百个机房，把你的静态文件复制过去。北京的用户由北京或天津的节点服务， 一个来回 5 毫秒。

它的两个动作

  1. 就近：DNS 会看你的来源，把你解析到最近的节点（或者用 Anycast，让网络路由自己把你带到最近那台）。
  2. 缓存：节点第一次没内容时，会「回源」去你的服务器取一次，然后存下来。之后一万个用户来，都直接由它给。

所以 CDN 的效果全看一个数字：命中率。图片、CSS、JS、视频这类静态资源，命中率能到 95% 以上； 而「你的购物车」「你的订单列表」这种每个人都不一样的内容，根本无法缓存，只能老老实实回源。 这就是为什么 CDN 厂商主打「静态加速」，动态页面还得靠别的手段。

一个十秒钟的小验证

F12 → Network → 随便点一个图片，看响应头里有没有 cf-cache-status: HIT 或 x-cache: HIT 之类的字段。有 HIT，说明你被 CDN 服务了； 看到 MISS，说明这个节点上还没有，它刚替你去源站取了一次。

但 CDN 救不了所有人

如果你的最后一公里是卫星（600 毫秒），CDN 把服务器搬到隔壁也没用 —— 信号还得飞一趟太空。 它省的是「跨城跨洲」，省不掉「上天下地」。这是下一节模拟器里可以亲手验证的事。

05

第五站：浏览器，收到图纸之后才开始干活

HTML 到你的电脑上了，但屏幕上还是白的。浏览器要做的活比大多数人想的多：

# 关键渲染路径 HTML 文本 → 解析成 DOM 树 （页面的骨架） CSS 文本 → 解析成 CSSOM （每个元素长什么样） ↓ 合起来 渲染树（只包含要显示的东西） ↓ 布局 Layout （每个盒子放哪、多大） ↓ 绘制 Paint （把颜色、文字、图片画成像素） ↓ 合成 Composite （分层拼成你看到的画面）

两个最常见的卡点

① CSS 会挡住渲染。浏览器必须等 CSS 下载并解析完才敢画第一笔 —— 因为先画一遍再改样式，用户会看到画面「闪一下重排」，比白屏更难受。 所以 CSS 要尽量小、尽量早、放在 <head> 里。

② <script> 默认会挡住解析。浏览器遇到一个普通脚本，会停下来： 下载、执行完，才继续解析后面的 HTML。一个慢脚本就能让整个页面白屏几秒。 解法是 defer（下载不挡解析，解析完按顺序执行）和 async（下载不挡，下完立刻执行）。 这也是为什么老教程让你「把 script 放在 </body> 前面」—— 那是没有 defer 时代的土办法。

白屏的三种真凶

现象多半是怎么确认
一直白，地址栏转圈网络段：DNS 卡住、TTFB 高、HTML 还没下来F12 Network 看那根最长的条
骨架出来了但样式全无CSS 没下载完，或被挡住了Network 里看 .css 的状态和耗时

诊断：网页变慢时，该看哪一段

打开开发者工具（F12）→ Network 面板 → 刷新页面。你会看到一张瀑布图： 每一行是一个请求，横向的彩色条是它的各个阶段，鼠标悬停能看到毫秒数。

这张图上有三种最典型的「形状」，看形状就知道该怪谁：

形状含义该优化什么
前面空一大段才开始排队（Queueing / Stalled），同时发的请求太多减少请求数、合并文件、懒加载
中间紫/绿色条很长等首字节（TTFB），服务器在思考后端、数据库、缓存 —— 换宽带没用
后面蓝色条很长下载慢，文件太大或带宽太小压缩、换格式（WebP）、上 CDN

一个常见误判

「我清了缓存反而更慢了」—— 对，因为你把最有用的一层优化手动删掉了。 清缓存是排查手段，不是优化手段。日常使用越少清越好。

本周挑战：给网速做一次分段体检

这周的三级挑战都不需要写代码，但需要你动手点几下。任选一级，做完就算赢。

Lv 1 · 观察 · 15 分钟 · 零代码

给自己常用的三个网站做体检

  • 选三个站：一个天天用的、一个国外的、一个小网站。
  • 每个站：F12 → Network → 勾「Disable cache」→ Ctrl+R 强制刷新。
  • 点最上面那行（HTML 文档）→ 右侧 Timing，记下 DNS、TCP、TLS、TTFB、下载 五个数。
  • 取消勾选再刷一次，记下「缓存后」的总时间。
  • 回答：三个站里哪一段占比最大？它们的答案一样吗？
Lv 2 · 动手 · 20 分钟 · 只改参数

用账单脚本验证「时间花在哪」

  • 跑 python latency_budget.py，再依次加 --cdn、--cached、--net satellite。
  • 先猜再跑：卫星的总时间是光纤的几倍？猜错了几倍？
  • 跑 --net satellite --cdn，解释：为什么给卫星用户加 CDN 也救不回来？
  • 把脚本里的 RENDER = 90 改成 900，看占比怎么反转。
Lv 3 · 探索 · 半小时

用 tracert 把「路」画出来

  • 对一个国内站和一个国外站各跑一次 tracert，找出延迟突然跳到 200ms+ 的那一跳。
  • 用 ping -n 10 看平均延迟和丢包率；再开手机热点对比一次。

带走三句话

  1. 网址不是地址，是一个需要翻译的名字。DNS 把名字换成 IP，路上每一层都在缓存 —— 所以「解析生效慢」是别人的缓存没过期，不是系统坏了。
  2. 慢的大头往往是「来回几次」，不是「数据多少」。光纤 20ms 意味着服务器在 2000 公里外； CDN 省的是距离，不是带宽；而卫星上网再贵的服务器也救不了。
  3. 白屏要分段查，不要整体骂。前面空 = 在排队，中间长 = 服务器在想， 后面长 = 文件太大，全都不长还卡 = 你的浏览器在忙。

三道自测

为什么同一个网站，我第一次打开要 2 秒，第二次只要 0.2 秒？

因为第一次走了全流程：查名字、建连接、上锁、要文件、下载、渲染。第二次这五步里有四步被缓存吃掉了 —— 名字记着、连接还热着、文件本地有（304 或 from disk cache），只剩渲染。 这不是「变快了」，是「大部分事没发生」。

我把网站搬到配置高十倍的服务器上，为什么同事还是说慢？

先看他卡在哪一段。如果他的 TTFB 很长，那是服务器/数据库的问题，换更强的机器确实有用； 但如果他的 DNS 和 TLS 就花了两百毫秒（比如人在国外、或者用的是卫星网络），那问题在距离上， 换服务器一点用都没有 —— 该做的是上 CDN，把内容搬到离他近的地方。

看到 502 和 404，哪个该找对方、哪个该改自己？

404 是「这个地址没有东西」，通常是你链接写错了或者页面被删了，该改自己。 502 是「网关去问后端，后端没应答」，是它的服务挂了，该等对方修。 记法就一句：4 开头是我的问题，5 开头是它的问题。

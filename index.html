01 Week 01 · Data Structures

布隆过滤器：用 1% 的误判，换掉 99% 的内存

它不存元素，只存"痕迹"。它说"不在"，那一定不在；它说"在"，你有 1% 的概率被骗。 就凭这一个不对称的承诺，它撑起了 Chrome 的恶意网址拦截、RocksDB 的读放大优化和无数缓存系统的第一道防线。

📖 阅读 约 18 分钟 🧩 项目挑战 3 个难度 🔧 参考实现 Python · 零依赖
00

先看一个真实的困境

你要给一个爬虫做 URL 去重。待抓队列里有 1 亿条 URL，机器上只给你 100 MB 内存做"见过没有"的判断。 直觉做法是一个哈希集合：

# 直觉做法 seen = set() seen.add("https://example.com/path?q=1") if url in seen: skip() # 账单 1 亿条 × 平均 60 字节 URL ≈ 6 GB 原始字符串 再叠加 Python 对象头 / 哈希表负载因子 ≈ 10 GB+ 预算 = 0.1 GB → 差了两个数量级，方案直接出局

这里其实藏着一个被忽略的假设：我们默认"判断是否见过"必须准确地回答。 但去重场景里，答错的代价并不对称：把一条没抓过的 URL 误判成"抓过了"而跳过，你只是少抓了一个页面； 把抓过的再抓一次，你只是浪费一次请求。两种错误都不致命。

一旦允许"偶尔出错"，问题的性质就变了：从精确成员查询变成近似成员查询， 而近似可以便宜到离谱 —— 上面那 10 GB 的活，布隆过滤器用 约 120 MB 就干完了（错判率 1%）。

空间不会凭空出现。你付出的代价不是内存，而是"确定性的方向"。
01

核心直觉：不记住内容，只记住痕迹

想象一间漆黑的仓库，地上有 m 个开关，每个开关只有"开"和"关"两种状态。 你要登记新来的货物，但仓库不允许你存放货物本身，只允许你拨动开关。

于是你定了一套规则：每件货物进门，用 k 台不同的"特征提取仪"各算出一个开关编号， 把这 k 个开关全部拨到"开"。以后有人问"这件货登记过吗"，你重新算一遍那 k 个编号，去看开关：

  • 只要有一个是关的 → 这件货绝对没登记过。这个判断 100% 可信。
  • 如果全是开的 → 可能是它开的，也可能是别的货物顺手把它拨开了。只能说"可能在"。

这就是布隆过滤器的全部。它的精妙之处在于放弃存储元素，只存储元素留下的痕迹， 而痕迹是可以被多件货物共享的 —— 共享带来了极致的空间效率，也带来了误判。

一句话定义

布隆过滤器是一个位数组 + k 个哈希函数构成的概率型集合：查询返回"一定不在"或"可能在"，永不返回假阴性，允许可控的假阳性。

02

数据结构：只有两样东西

整个结构只有两个参数，没有别的：

符号含义典型值
m位数组长度（bit 数）958,506（为 10 万元素、1% 误判设计）
k哈希函数个数7
n已插入元素个数（运行时状态）≤ 设计容量

注意 m 的单位是 比特，不是字节。这是它能省下三个数量级的根本原因： 存一个元素平均只花 m/n ≈ 9.6 个比特，而一个 URL 字符串要 480 个比特。

插入与查询的完整流程

查询时只需要重算 h₁…h_k 并逐位检查，没有任何字符串比较，没有指针追逐，全部是数组随机访问。 这也是它比哈希表快的原因：一次查询只有 k 次内存访问，且命中率极高。

04

为什么假阴性不可能发生

这是面试里最常被追问的一点，也是它安全性的根基。证明只需要一句话：

单调性论证

位数组的每一位只会从 0 → 1，永远不会从 1 → 0（没有删除操作）。
元素 x 插入时把它命中的 k 位全部置 1；此后这些位永远是 1。
因此再次查询 x 时，那 k 位必然都是 1 → 必然返回"可能在"。假阴性在结构上被排除了。

反过来，假阳性之所以可能，是因为别的元素可能恰好把 x 的 k 个位置全占了。 随着插入元素变多，位数组越填越满，这种"撞车"的概率单调上升 —— 这就是为什么布隆过滤器必须在创建时确定容量。

工程含义

如果实际插入量超过设计容量 2 倍，1% 的误判率会恶化到 30% 以上，过滤器基本报废。 生产环境要么留足 1.5~2 倍余量，要么使用可扩展布隆过滤器（Scalable Bloom Filter：满了就新建一层，容量翻倍、误判率乘 0.5）。

还有一个隐藏性质：布隆过滤器不能删除元素。因为一个位可能被多个元素共享， 你把某位清 0，会顺手"抹掉"其他元素的记录，从而制造出假阴性 —— 唯一不能破坏的承诺被破坏了。 想支持删除，需要升级成计数布隆过滤器（每位用 4 bit 计数器代替 1 bit），代价是内存变 4 倍。

05

把误判率算出来：三行推导

这一节是本期真正的"知识增量"。推导不难，但每一步都值得自己动手写一遍。 假设哈希函数理想均匀（每个位置被选中的概率都是 1/m，彼此独立）。

第 1 步：插入一个元素后，某一位还是 0 的概率

一次哈希不会选中这一位的概率是 1 − 1/m；k 次哈希都没选中：

P(仍为 0) = (1 − 1/m)k ≈ e−k/m // 用 (1−1/m)^m → 1/e

第 2 步：插入 n 个元素后，某一位还是 0 的概率

n 个元素一共做了 kn 次哈希：

P(仍为 0) = (1 − 1/m)kn ≈ e−kn/m P(为 1) = 1 − e−kn/m

第 3 步：查询一个不存在的元素，k 位恰好全为 1 的概率

p ≈ (1 − e−kn/m)k // 这就是误判率公式

这个公式是布隆过滤器的"物理定律"。它告诉你三件事：n 越大 p 越大； m 越大 p 越小；而 k 有一个最优值 —— 因为 k 增大既让"每位更满"（坏）， 又让"需要全部命中"更难（好），两者在某个点平衡。

最优 k 与所需空间

对 p 关于 k 求导令其为零，得到：

kopt = (m/n) · ln2 ≈ 0.693 · (m/n) 代入原式：pmin = (1/2)k = 0.6185m/n 反解出每元素所需比特数： m/n = −ln(p) / (ln2)² ≈ 1.44 · log₂(1/p)

于是有这张"背下来就能用"的参数表：

目标误判率 p每元素比特 m/n最优 k100 万元素实际内存哈希表（对照）
10%4.793≈ 0.6 MB≈ 100 MB 起
且随负载因子线性增长
1%9.597≈ 1.2 MB
0.1%14.3810≈ 1.8 MB
0.01%19.1713≈ 2.4 MB

注意最后一行到第一行的跨度：把误判率从 10% 压到 0.01%，内存只涨了 4 倍。 这是对数级的性价比 —— 每多付 1.44 bit/元素，误判率降一个数量级。 这也是为什么布隆过滤器常常被"过度配置"：反正便宜。

一个常被忽略的细节

公式里的 k 是哈希函数个数，实现里通常用双哈希技巧 gᵢ(x) = (h₁(x) + i·h₂(x)) mod m 模拟 k 个独立哈希（Kirsch–Mitzenmacher 定理）， 只需算两个哈希就能得到 k 个位置，速度提升 k/2 倍。本页演示与参考实现都用这个方法。

06

它在哪些地方真正跑着

布隆过滤器不是课本玩具。以下是几个你每天都在用的部署：

系统用法为什么值得
Chrome / Safe Browsing 本地存一份恶意 URL 前缀的布隆过滤器，命中后才向 Google 发完整查询 避免每次导航都联网校验，同时不泄露你访问了哪些正常网站
RocksDB / LevelDB 每个 SST 文件附带一个过滤器；查 key 前先问它"这个文件里可能有吗" 省掉绝大多数无意义的磁盘 IO，直接缓解 LSM-tree 的读放大
HBase / Cassandra 每个 HFile 一个过滤器，RegionServer 先过滤再读盘 随机读延迟从"扫多个文件"降到"只读一个"
Redis SETBIT/GETBIT 手搓，或用 RedisBloom 模块的 BF.ADD 缓存穿透防护：拦住查不存在的 key 的请求，别让它们打到数据库
CDN / 爬虫 URL 去重、已缓存资源判定 亿级规模下内存是硬约束，错判 1% 完全可以接受

手写一个最朴素的版本，只要 30 行

理解它最好的方式是先写一个"能跑但很慢"的版本，再逐步优化：

# 教学版：用 set 存位置，强调逻辑而非性能 import hashlib, math class Bloom: def __init__(self, n, p=0.01): self.m = math.ceil(-n * math.log(p) / math.log(2)**2) self.k = round(self.m / n * math.log(2)) self.bits = set() def _pos(self, x): h1 = int(hashlib.md5(x.encode()).hexdigest(), 16) h2 = int(hashlib.sha1(x.encode()).hexdigest(), 16) return [(h1 + i*h2) % self.m for i in range(self.k)] def add(self, x): self.bits.update(self._pos(x)) def __contains__(self, x): return all(i in self.bits for i in self._pos(x))

完整版（week-01/bloom.py）在这个骨架上做了四件事：用 bytearray 按位存储（内存降到 1/8 以下）、 用 blake2b 双哈希（进程间稳定）、跟踪置位计数以实时估算误判率、以及用填充率反推元素个数。

上生产前必须知道的坑

  • 别用语言内置 hash()。Python 的 hash() 对字符串每个进程加了随机盐，重启后过滤器全废。要用 MD5/SHA/blake2 这类稳定哈希。
  • k 不是越大越好。k 超过最优值后误判率反而上升，而且查询变慢 k 倍。按公式算。
  • 容量必须事先估。m 一旦定死改不了。宁可多留 50% 余量。
  • 分布式场景要小心。多个节点各持一份会不一致；共享一份要考虑并发写位数组的原子性（Redis SETBIT 是原子的，这也是它适合做布隆的原因）。
  • 它不能枚举、不能计数。需要"取出所有元素"或"精确计数"就得换结构。
07

什么时候不该用它

一个诚实的知识介绍，必须说清边界。以下情况请换方案：

需求该用什么相对布隆的代价
需要删除元素计数布隆过滤器 / 布谷鸟过滤器4× 内存 / 略高但更可预测的误判
需要零误判哈希表、B 树、Roaring Bitmap内存高一个数量级以上
需要取出元素任何真正的集合结构布隆过滤器从设计上就不可枚举
容量会持续增长且无法预估Scalable Bloom Filter（分层）层数越多误判率越高，需按 0.5 递减分配
误判率要压到 0.001% 以下还要省空间Ribbon Filter / XOR Filter实现复杂，但比布隆再省 30% 空间

顺带一提演进脉络：Bloom（1970）→ Counting Bloom（删）→ Cuckoo Filter（可删、更省、查更快）→ Quotient / Ribbon Filter（RocksDB 现在默认用它）。 这条线本身就是一部"用更聪明的编码榨干每一个比特"的历史，值得单独做一期。

五道自测题

先自己回答，再点开对照。答不上来说明还没读懂，回去看对应小节。

为什么布隆过滤器不可能出现假阴性？

因为位只会 0→1 单向变化。元素插入时把自己命中的 k 位全部置 1，之后没有任何操作会把它们清 0，所以再次查询必然全部命中。假阴性只可能来自"删除操作"或"比特位被并发覆盖"这类破坏单调性的实现 bug。

100 万元素、要求 0.1% 误判率，需要多少内存和几个哈希函数？

由表可得 m/n ≈ 14.38 bit，k = 10。总空间 = 100 万 × 14.38 bit ≈ 14.38 Mbit ≈ 1.8 MB。对照：存 100 万个 20 字节的字符串至少 20 MB，实际含哈希表开销通常是 60~100 MB。省下约 40 倍。

我把 k 从 7 调到 14（m、n 不变），误判率会降低吗？

不会，反而升高。k 增大使每个元素点亮更多位，位数组更快变满（P(位为1) 上升），而"k 位全为 1"这个条件虽然更严，但前者的效果占优。当 k 超过 (m/n)·ln2 后，误判率就单调上升了。公式 p=(1−e^(−kn/m))^k 对 k 求导可以严格证明这一点。

为什么实现里常用"双哈希"而不是真的写 7 个哈希函数？

因为 Kirsch–Mitzenmacher 证明了：用两个独立哈希 h₁、h₂ 构造 gᵢ = (h₁ + i·h₂) mod m，其渐近误判率与 k 个真正独立的哈希函数相同。这样每次查询只需算 2 次哈希而不是 k 次，CPU 开销大幅下降，且代码更短。

缓存穿透防护里，布隆过滤器应该放在哪一侧？为什么不能直接缓存空结果？

放在缓存前面（请求先过过滤器，未命中直接返回）。「缓存空值」也能防穿透，但攻击者可以用大量互不相同的随机 key 打进来，每个都产生一条空值缓存，把缓存本身撑爆（内存攻击）。布隆过滤器对任意多个不存在的 key 只占固定内存，这正是它不可替代的地方。

带走三句话

  1. 布隆过滤器交易的是确定性，不是精度。它把"可能错"的方向固定成单向 —— 只会误报"在"，绝不误报"不在"。这种不对称让它在工程上极其安全。
  2. 空间效率来自共享。m 个比特记录 n 个元素，靠的是碰撞。碰撞是 bug 也是 feature，关键看你能否给碰撞定价（1% 误判是否可接受）。
  3. 公式比代码重要。m/n = −ln(p)/(ln2)² 这一行决定了整个系统的容量规划，写错参数比写错循环危险得多。

# Week 03 · 本周挑战：给你的网速做一次「分段体检」

> 本期不考算法、不考编程。三级任选，**做完任意一级都算赢**。
> 需要的工具你电脑上都有：Chrome / Edge 的开发者工具（F12）、一个命令行窗口。

---

## 先说清楚这次要练的是什么

「网站好慢」是一句没用的话。**有用的话长这样：**

> 「这个站首字节用了 1.8 秒，DNS 和 TLS 都只有 20 毫秒，所以慢在服务器，不在网络。」

这期练的就是把一句抱怨拆成一句结论。方法只有一个：**看瀑布图，找最长的那一段。**

---

## Lv 1 · 观察 · 15 分钟 · 零代码

### 给自己常用的三个网站做体检

对下面三个网站各做一次：

1. 你每天都会打开的（比如 B 站 / 知乎 / 学校教务）
2. 一个国外的（比如 `github.com`、`wikipedia.org`）
3. 一个小网站（个人博客、学校某部门页面都行）

**步骤**

1. 打开网站 → 按 `F12` → 切到 **Network**（网络）面板 → 勾上「Disable cache」。
2. 按 `Ctrl + R`（Mac 是 `Cmd + R`）**强制刷新**，等页面加载完。
3. 点最上面那一行（一般就是那个 HTML 文档），看右侧 **Timing** 标签页。
4. 把五个数字填进表里：**DNS、Initial connection（TCP）、SSL（TLS）、Waiting（TTFB）、Content Download**。
5. 再取消勾选「Disable cache」，普通刷新一次，看总计变成了多少。

**你要交的是一张这样的表：**

| 网站 | DNS | TCP | TLS | TTFB | 下载 | 总计（首次） | 总计（缓存后） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 例：bilibili.com | 3 ms | 18 ms | 35 ms | 210 ms | 40 ms | 1.2 s | 380 ms |
| 网站 A | | | | | | | |
| 网站 B | | | | | | | |
| 网站 C | | | | | | | |

**然后回答三个问题（各一句话就够）：**

- 三个网站里，**哪一段占比最大**？它们的答案一样吗？
- 哪一个网站「缓存后」提速最明显？为什么是它？
- 有没有哪个网站的 TTFB 超过 500 毫秒？如果它是国内站，这说明什么？

> 💡 小技巧：如果 Timing 里只看到 Total 和 Waiting，说明这个请求复用了已有连接 ——
> 先点一下别的网站再回来，或者开一个无痕窗口，才能看到完整的 DNS/TCP/TLS。

## Lv 2 · 动手 · 20 分钟 · 改 3 个参数

### 用账单脚本验证「时间花在哪」

仓库里有个零依赖的小脚本，它把讲义第 06 节那张表算出来：

```bash
cd week-03
python latency_budget.py                 # 光纤 + HTTPS + 无 CDN + 首次访问
python latency_budget.py --net 4g        # 换成 4G
python latency_budget.py --cdn           # 加上 CDN
python latency_budget.py --cached        # 第二次访问（缓存命中）
python latency_budget.py --no-https      # 不走 HTTPS
```

**任务**

1. 先**不看输出**，猜一下：`--net satellite`（卫星，RTT 600ms）的总时间大概是光纤的几倍？写下来。
2. 跑一遍，对比你的猜测。差多少？差在哪一段？
3. 跑 `--cached`，看总时间。**这就是缓存的价值：它不是让事情变快，是让大部分事情不用发生。**
4. 跑 `--net satellite --cdn`，然后回答：**为什么给卫星用户加 CDN 也救不回来？**
5. 打开 `latency_budget.py`，把 `RENDER = 90` 改成 `900`（模拟一个又大又重的页面），再跑一次，看占比怎么变。

**验收标准**：能说清「CDN 省的是哪一段、省不掉哪一段」。

<details>
<summary>参考答案（先自己试，别急着点）</summary>

- 卫星是光纤的 **7 倍多**（2685ms vs 365ms）：光纤总共只花 4 个往返，卫星 4 个往返就是 2.4 秒。
  这就是「延迟的主导因素是来回次数，不是数据量」。
- **CDN 省的是「跨城 / 跨洲」那一段，省不掉最后一公里。** 卫星的 600ms 里大半是「上天下地」，
  不管服务器搬到多近，信号都得飞一趟太空。所以模型里 `path` 最多减 150ms（2685 → 1973，快了 26%，
  但仍然是光纤的 5 倍多）。
- RENDER 改成 900 之后，占比立刻反转到渲染这一段 —— **同一张账单，瓶颈会换人**。
  这也是为什么优化前必须先测量。

</details>

## Lv 3 · 探索 · 半小时 · 找慢在哪一跳

### 用 `tracert` 把「路」画出来

`ping` 只告诉你总时间，`tracert`（Mac / Linux 是 `traceroute`）会告诉你**每一跳**的时间：

```bash
# Windows
tracert github.com

# macOS / Linux
traceroute github.com
```

你会看到十几行，每行是路径上的一个路由器，三列是三次探测的毫秒数。

**任务**

1. 对**一个国内站**和一个**国外站**各跑一次，把结果贴进 Issue。
2. 找出**延迟突然从几十毫秒跳到两百毫秒以上**的那一跳 —— 那一跳之后，数据就出国了。
3. 再跑一次 `ping -n 10 github.com`（Mac 用 `ping -c 10`），看**平均延迟和丢包率**。
4. 用手机开热点，让电脑连热点，重复第 3 步。对比一下 Wi-Fi 和 4G 的 RTT。
5. 最后回答一个问题：**如果让你把这个国外网站变快，你能做的事有哪几件？**
   （提示：你不能改变光速，但你可以改变「数据要跑多远」和「要跑几趟」。）

**加分项**：算一下你到那台服务器的物理距离上限。
`单程时间 × 20 万公里/秒 = 理论最远距离`。如果实际距离比这个还远，说明什么？
（提示：绕路。海底光缆不是直线。）

## 一个提醒

体检出来的数字会远小于你「感觉」的等待时间。这不是测错了 ——
你感觉到的「慢」里，还混着服务器端渲染、广告脚本、视频预加载、以及你自己那台开了 40 个标签页的电脑。
**先把能测的那部分测清楚，剩下的才有得谈。**

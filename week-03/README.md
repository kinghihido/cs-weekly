## 00 · 那 0.4 秒里，发生了大约 30 次跨城甚至跨洲的往返

你在地址栏敲下 `kinghihido.github.io`，回车。屏幕闪了一下，页面出现了。

感觉像「打开了一个文件」。实际上，在你看不见的这几百毫秒里，你的电脑和世界各地的一堆机器
完成了一连串对话：查地址、建立连接、加密、发请求、等回复、下载、再下载十几个附件、排版、画字。
**每一步都可能变慢，而且变慢的原因完全不同。**

这期我们要做的事只有一件：**把这 0.4 秒拆成五段，让你知道每一段在干什么。**
拆开之后你会发现，「网站怎么这么慢」不再是一个含糊的抱怨，而是一个可以定位的问题 ——
是名字没查到？路没修通？服务器在忙？文件太大？还是你的浏览器在忙着跑脚本？

> **先破一个常见的想象**
> 很多人以为「网站」是存在某个地方的**一个文件夹**，打开网址就是去那个文件夹里把文件取回来。
> 前面的部分对，后面的部分不对：**你取回来的只有一张「施工图」（HTML），
> 油漆、瓷砖、家具（CSS、JS、图片）是浏览器看完图纸后，又跑了好几趟分别取回来的。**
> 所以「网页打开慢」经常不是 HTML 慢，而是后面那十几趟慢。

## 01 · 第一站：DNS —— 把名字翻译成地址

### 名字和地址是两套东西

`kinghihido.github.io` 这个名字，机器完全看不懂。机器只认 IP 地址，比如 `185.199.108.153`。
**DNS（域名系统）就是那本电话簿**：你报名字，它给你号码。

为什么不用号码直接上网？因为电话号码会变，名字不会。GitHub 明天把服务器搬到另一个机房，
IP 变了，但 `github.io` 这个名字不用变 —— **名字是给人用的稳定入口，IP 是给机器用的临时坐标。**
这就是「域名」存在的全部理由。

### 查一次名字，可能要问四五个人

DNS 不是一个中央大数据库，而是一层一层的「我不知道，但我知道该问谁」：

```
你的浏览器          自己先翻一遍缓存（刚访问过？）
   ↓ 没有
你的操作系统        再翻一遍（还有 hosts 文件，可以手动写死）
   ↓ 没有
递归解析器          通常是运营商给的，或者你设的 8.8.8.8 / 223.5.5.5
   ↓ 它替你跑腿，从最顶上开始问
根服务器 "."        回答：我不知道 github.io，但 .io 的服务器在那边
   ↓
顶级域服务器 .io    回答：我也不知道，但 github.io 的权威服务器在那边
   ↓
权威 DNS            这里才真正存着 IP，回答 185.199.108.153，顺便说一句「这个答案可以记 300 秒」
   ↓
原路返回，每一层都把自己那份缓存写上
```

第一次查要跑这一整圈。第二次就不同了 —— 浏览器自己记着，**0 毫秒**。

### 三个天天遇到、但很少人想明白的现象

**① 为什么改了 DNS 解析，要等几小时甚至一天才生效？**
因为路上每一层都缓存了旧答案，而那条「可以记 300 秒」的指令（叫 **TTL**）是域名主人自己设的。
你改了记录，但别人手里的旧答案还没过期。所谓「DNS 生效慢」，本质是**全世界几十万台缓存服务器
在等你上一次设的 TTL 走完**。所以迁移前要做的第一件事是把 TTL 调小。

**② 为什么「网站打不开」有时是 DNS 的问题？**
如果名字查不到，浏览器连门都找不到，错误提示通常是「找不到服务器 / DNS 解析失败」。
这时候换一个 DNS（比如手机热点），如果立刻能开，问题就锁定在解析这一层，和网站本身无关。

**③ 一个域名不等于一台服务器。**
`baidu.com` 背后是成千台机器，DNS 每次可能给你不同的 IP（这叫负载均衡）；
反过来，一台服务器上也可能放着几百个网站（虚拟主机）。
所以「同一个 IP 上有几万个网站」是正常的，不是有人蹭你的服务器。

## 02 · 第二站：握手 —— TCP 建立连接，TLS 上锁

拿到 IP 之后，浏览器还不能直接喊话。它得先和对方**建立一条可靠的连接**。

### TCP：先互相确认「你听得到我吗」

网络是不可靠的：包会丢、会乱序、会重复。TCP 在不可靠的底子上做出一根「看起来可靠的管子」，
第一件事是三次握手：

```
你  → 服务器    SYN       （在吗？我想连你）
服务器 → 你     SYN+ACK   （在，我听到你了，你听得到我吗？）
你  → 服务器    ACK       （听得到，开始吧）
```

注意代价：**这个过程要花掉一个「来回」**（一个 RTT，往返时间）。不是三次传输的时间，是一次往返的时间。
家里光纤的 RTT 大概 10~30 毫秒；4G 大概 30~60 毫秒；卫星上网能到 600 毫秒以上。

### TLS：在管子里再套一层加密

HTTPS 不是「另一个协议」，而是「HTTP 跑在一条加了密的管子里」。开这条管子要额外一次往返：
验证对方证书是不是真的、协商出一把只有双方知道的钥匙。

**这里有个反直觉的结论：延迟的大头不是「数据多少」，而是「来回几次」。**
一个 1 KB 的请求和一个 1 MB 的请求，在 100 Mbps 的宽带上传输时间差 80 毫秒；
但每多一次跨洲往返就是 200 毫秒起。这就是为什么工程师拼命减少「往返次数」——
HTTP/2 把多个请求塞进一条连接、HTTP/3 干脆把握手也省了、TLS 1.3 把两次往返压成一次。

### 顺手算一个物理极限

光在光纤里的速度大约是 20 万公里/秒（不是真空的 30 万，玻璃里会慢三分之一）。
**一个来回 20 毫秒，意味着服务器离你大约 2000 公里。** 北京到上海约 1200 公里，
北京到洛杉矶约 10000 公里 —— 单程 50 毫秒，一个来回 100 毫秒。
所以「打开一个美国网站，不管它服务器多强，都至少比国内站慢 100 毫秒」，
这不是优化问题，是**光速问题**，谁也没法修。

> **所以「多握手几次」在小网站上很贵**
> 一个页面如果对 30 个不同域名各建立一次连接，每次 3 个往返，在卫星网络上就是
> 30 × 3 × 600 毫秒 ≈ **54 秒**。这不是夸张，这是很多老网站在偏远地区打不开的真实原因。
> 现在的好做法是：把资源放在同一个域名下、复用连接、用 CDN 把服务器搬到离你几十公里的地方。

## 03 · 第三站：HTTP —— 那张递进去的纸条

连接通了、锁上好了，浏览器终于可以说话了。它说的话非常朴素，就是一张纸条：

```
GET /index.html HTTP/1.1          ← 我要什么（方法 + 路径 + 协议版本）
Host: kinghihido.github.io        ← 我要找哪一家（同一个 IP 上可能住着几百家）
User-Agent: Chrome / Windows      ← 我是谁（顺便让网站知道给你哪个版本）
Accept: text/html                 ← 我能吃什么样的内容
Accept-Encoding: gzip, br         ← 我能解压，你压缩了再发，省流量
Cookie: session=abc123            ← 上次你给我的那张小纸条，我还带着
```

服务器回一张纸条加一个包裹：

```
HTTP/1.1 200 OK                   ← 状态码：办成了
Content-Type: text/html           ← 包裹里是什么
Content-Length: 15234             ← 多大
Cache-Control: max-age=600        ← 这个可以缓存 10 分钟
                                          ↓ 空一行，然后是内容
<!DOCTYPE html> ...               ← 真正的 HTML
```

### 状态码：三秒看懂一张表

| 开头 | 谁的问题 | 常见成员 |
| --- | --- | --- |
| **2xx** 成功 | 都没问题 | `200` 正常、`204` 成功但没内容 |
| **3xx** 搬家 | 你去别处 | `301` 永久搬走、`302` 临时搬走、`304` **你手里的没过期，直接用** |
| **4xx** 你的问题 | 请求不对 | `401` 没登录、`403` 没权限、`404` 没有这个页面、`429` 你请求太快被限流 |
| **5xx** 它的问题 | 服务器崩了 | `500` 代码炸了、`502` 上游没响应、`503` 太忙了、`504` 上游超时 |

记住一条就够用：**4 开头是你敲错了或者没权限，5 开头是它自己出事了。**
看到 502/504 别再刷新了，那是它的问题，刷新一百次也一样。

### Cookie：为什么你关掉浏览器再打开，还是登录状态

HTTP 本身是**失忆的**：每个请求都是独立的，服务器不记得上一个请求是谁发的。
所以登录成功后，服务器在响应里塞一句 `Set-Cookie: session=abc123`，浏览器存下来，
之后每次请求自动带上。**「登录状态」本质上就是一张每次都要出示的通行证。**

这也解释了两件事：

- 为什么 Cookie 不能存太多东西（每次请求都要带，会拖慢每一个请求）；
- 为什么图片、CSS 这类资源常放在另一个「不带 Cookie 的域名」上 —— 少带几百字节，乘以几十个请求就不是小数。

## 04 · 第四站：CDN —— 为什么不从美国给你搬

假设你的服务器在硅谷，用户在北京。就算服务器是全世界最快的，也没用：
数据得跨太平洋，一个来回 100 毫秒，每次握手、每个请求都要走这一趟。

**CDN（内容分发网络）解决的就是这个「距离」问题，而不是「速度」问题。**
它在全世界放几百个机房，把你的静态文件复制过去。北京的用户由北京或天津的节点服务，
一个来回 5 毫秒。

它的魔法有两个：

1. **就近**：DNS 会看你的来源，把你解析到最近的节点（或者用 Anycast，让网络路由自己把你带到最近的一台）。
2. **缓存**：节点第一次没内容时，会「回源」去你的服务器取一次，然后存下来。之后一万个用户来，都直接由它给。

所以 CDN 的效果取决于一个数字：**命中率**。静态资源（图片、CSS、JS、视频）命中率能到 95% 以上；
而「你的购物车」「你的订单列表」这种每个人都不一样的内容，**根本无法缓存**，只能老老实实回源。
这就是为什么 CDN 厂商卖的是「静态加速」，动态页面还得靠别的手段（边缘计算、数据库优化）。

> **一个小验证**
> 在浏览器里按 F12 → Network → 随便点一个图片，看响应头里有没有
> `cf-cache-status: HIT` 或 `x-cache: HIT` 之类的字段。有 HIT，说明你被 CDN 服务了；
> 看到 `MISS`，说明这个节点上还没有，它刚去源站取了一次。

## 05 · 第五站：浏览器 —— 收到图纸之后才开始干活

HTML 到手机/电脑上了，但屏幕上还是白的。浏览器要做的活比大多数人想的多：

```
HTML 文本  →  解析成 DOM 树      （页面的骨架）
CSS 文本   →  解析成 CSSOM       （每个元素长什么样）
                    ↓ 合起来
              渲染树（只包含要显示的东西）
                    ↓
              布局 Layout        （每个盒子放在哪个坐标、多大）
                    ↓
              绘制 Paint         （把颜色、文字、图片真正画成像素）
                    ↓
              合成 Composite     （分层拼成你看到的画面）
```

这个流程有个名字叫**关键渲染路径**。它决定了「你多久能看到东西」。

### 两个最常见的卡点

**① CSS 会挡住渲染。** 浏览器必须等 CSS 下载并解析完才敢画第一笔 ——
因为如果先画一遍再改样式，用户会看到画面「闪一下重排」，比白屏更难受。
所以 CSS 要尽量小、尽量早、尽量放在 `<head>` 里。

**② `<script>` 默认会挡住解析。** 浏览器遇到一个普通 `<script>`，会**停下来**：
下载、执行完，才继续解析后面的 HTML。一个慢脚本就能让整个页面白屏几秒。
解法是 `defer`（下载不挡解析，解析完再按顺序执行）和 `async`（下载不挡，下完立刻执行）。
这也是为什么老教程都让你「把 script 放在 `</body>` 前面」—— 那是没有 defer 时代的土办法。

### 白屏的三种真凶

看到「一直白屏」时，先别骂网速，可能是三种完全不同的原因：

1. **网络段慢**：DNS 卡住、TTFB 高、或 HTML 还没下载完 —— 打开 DevTools 的 Network 一眼就能看出来。
2. **渲染被挡住**：CSS/JS 在排队，或者一个同步脚本在等一个永远不返回的接口。
3. **根本不是网络**：字体文件太大（文字等字体才显示）、首屏图片是几 MB 的原图、或者 JS 在算一个死循环。

区分方法在下一节。

## 06 · 把这五站串起来：时间到底花在哪

把刚才五段拼起来，一个「首次访问」的账单大概长这样（家庭光纤，RTT 20ms）：

| 阶段 | 干什么 | 典型耗时 | 能不能优化 |
| --- | --- | --- | --- |
| DNS 解析 | 名字 → IP | 0 ~ 100 ms | 缓存、预解析、换更快的 DNS |
| TCP 握手 | 建立连接（1 个来回） | 1 × RTT | 复用连接、减少域名数 |
| TLS 握手 | 验证 + 协商密钥（1 个来回） | 1 × RTT | TLS 1.3、会话复用（0-RTT） |
| 请求 + 等首字节 | 服务器接单、查数据、生成页面 | 20 ~ 500 ms | 后端优化、缓存、CDN |
| 下载 HTML | 把图纸传回来 | 10 ~ 100 ms | 压缩（gzip/brotli）、减小体积 |
| 拉取 CSS/JS/图 | 图纸上写的材料，再跑十几趟 | 50 ~ 500 ms | 合并、压缩、CDN、懒加载 |
| 解析与渲染 | 排版、画像素 | 50 ~ 300 ms | 减少 DOM、别用阻塞脚本 |

**看这张表最重要的一点：没有任何一段是「大部分」。** 每个环节都占 10%~30%，
所以「网站慢」永远要做体检，不能拍脑袋猜。这也解释了为什么有些优化「感觉没用」——
你优化了下载体积，可瓶颈其实在服务器等数据库。

至于「第二次访问为什么飞快」：因为上面五行里有四行可以直接跳过。
名字查过了、连接还热着、文件还在本地缓存（`304 Not Modified` 或 `from disk cache`）——
只剩下渲染。**这就是缓存的价值：它不是让东西变快，而是让大部分事根本不用发生。**

## 07 · 诊断：网页变慢时，该看哪一段

打开浏览器的开发者工具（F12）→ **Network** 面板 → 刷新页面。你会看到一张「瀑布图」，
每一行是一个请求，横向的彩色条是它的各个阶段。鼠标悬停能看到具体毫秒数。

三种最典型的形状：

**① 前面空了一大段才开始** —— 排队（Queueing / Stalled）。
说明浏览器同时在发的请求太多，或者连接数被占满了。常见于「一个页面 80 个图片」。

**② 紫色/绿色条很长（Waiting / TTFB）** —— 服务器慢。
浏览器已经把请求送到了，是对方在思考。这时候你优化图片、换 CDN 都没用，
该查的是服务器和数据库。

**③ 蓝色条很长（Content Download）** —— 文件太大或你的带宽太小。
看这个请求有多少 MB，一张 5 MB 的首屏大图，在手机 4G 上就是几秒。

再配三个命令行/系统工具，基本能定位九成问题：

| 症状 | 先查什么 | 说明 |
| --- | --- | --- |
| 只有我打不开，别人正常 | `nslookup 域名`、换个网络试 | 多半是本地 DNS 缓存、hosts、代理或防火墙 |
| 所有网站都慢 | `ping 223.5.5.5` | 看 RTT 和丢包，判断是路由器/宽带还是终端 |
| 某个国外站特别慢 | `tracert 域名`（Mac 用 `traceroute`） | 看从第几跳开始从 20ms 跳到 200ms，那一段就是拥堵点 |
| 第一次慢、刷新就快 | Network 里看 `304` / `from disk cache` | 缓存生效了，不是故障 |
| 页面出来了但滚动卡 | 换到 Performance 面板 | 这不是网络问题，是渲染/JS 在主线程上堵着 |

> **一个常见误判**
> 「我清了缓存反而更慢了」—— 对，因为你把最有用的一层优化手动删掉了。
> 清缓存是排查手段，不是优化手段。日常使用越少清越好。

## 08 · 带走三句话

1. **网址不是地址，是一个需要翻译的名字。** DNS 把名字换成 IP，路上每一层都在缓存，
   所以「解析生效慢」是缓存过期，不是系统坏了。
2. **慢的大头往往是「来回几次」，不是「数据多少」。** 光纤 20ms 意味着服务器在 2000 公里外；
   CDN 真正省的是距离，不是带宽。
3. **白屏要分段查，不要整体骂。** F12 的瀑布图把这 0.4 秒拆开摆在眼前：
   前面空 = 排队，中间长 = 服务器在想，后面长 = 文件太大，全都不长还卡 = 你的浏览器在忙。

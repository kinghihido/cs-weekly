## 1. 问题的形状

爬虫要去重 1 亿条 URL，机器只给 100 MB 内存判断"这条见过没有"。

哈希集合的账单：1 亿条 × 60 字节 ≈ 6 GB 原始字符串，叠加对象头和哈希表负载因子约 10 GB，差两个数量级，直接出局。

被忽略的假设是：**"判断是否见过"必须准确回答**。但在去重场景里，答错的代价并不对称 —— 误判成"抓过"只是少抓一页，重复抓也只是浪费一次请求。两种错误都不致命。

一旦允许"偶尔出错"，问题就从**精确成员查询**变成**近似成员查询**，而近似可以便宜到离谱：上面那 10 GB 的活，布隆过滤器用约 **120 MB** 干完（1% 误判率）。

> 空间不会凭空出现。你付出的代价不是内存，而是"确定性的方向"。

## 2. 核心直觉：不记住内容，只记住痕迹

想象一间仓库，地上有 `m` 个开关，每个只有开/关。你不允许存放货物本身，只能拨开关。

规则：每件货进门，用 `k` 台特征提取仪各算出一个开关编号，把这 `k` 个开关拨到"开"。以后有人问"这件货登记过吗"，重算编号去看开关：

- 只要有一个是关的 → **绝对没登记过**（100% 可信）
- 全是开的 → **可能登记过**，也可能是别的货顺手拨开的（假阳性）

这就是全部。精妙之处在于**放弃存储元素，只存储元素留下的痕迹**，而痕迹可以被多件货共享 —— 共享带来极致的空间效率，也带来误判。

---

## 3. 数据结构：只有两样东西

| 符号 | 含义 | 典型值（10 万元素 / 1% 误判） |
| --- | --- | --- |
| `m` | 位数组长度（**bit**） | 958,506 |
| `k` | 哈希函数个数 | 7 |
| `n` | 已插入元素数（运行时） | ≤ 设计容量 |

`m` 的单位是比特，这是省下三个数量级的根本原因：平均每元素只花 `m/n ≈ 9.6` bit，而存一个 URL 字符串要 480 bit。

**插入**：算 k 个位置，全部置 1。
**查询**：算 k 个位置，全为 1 则"可能在"，任一为 0 则"一定不在"。

没有字符串比较，没有指针追逐，只有 k 次数组随机访问 —— 这也是它比哈希表快的原因。

---

## 4. 为什么没有假阴性

一句话证明：**位数组只会 `0 → 1`，永不 `1 → 0`**。

元素 x 插入时把它命中的 k 位全部置 1；此后没有任何操作会把它们清 0。再查 x 时那 k 位必然都是 1 → 必然返回"可能在"。假阴性在结构上被排除。

反过来，假阳性之所以可能，是因为别的元素恰好把 x 的 k 个位置全占了。插入越多，位数组越满，撞车概率单调上升 —— 所以**容量必须在创建时确定**。

两个直接推论：

1. **不能删除**。一个位可能被多个元素共享，清 0 会抹掉别人的记录，制造出假阴性 —— 唯一不能破坏的承诺被破坏。要删就用计数布隆过滤器（每位 4 bit 计数器，内存 ×4）。
2. **超载会崩溃**。实际插入量达到设计容量 2 倍时，1% 会恶化到 30%+。生产要么留 1.5~2 倍余量，要么用可扩展布隆过滤器（Scalable Bloom Filter：满了新建一层，容量翻倍、目标误判率乘 0.5）。

## 5. 误判率推导

假设哈希理想均匀：每个位置被选中概率均为 `1/m`，相互独立。

**第 1 步** 插入一个元素后，某一位仍是 0 的概率：

```
P(仍为 0) = (1 − 1/m)^k ≈ e^(−k/m)        // 用 (1−1/m)^m → 1/e
```

**第 2 步** 插入 n 个元素（共 kn 次哈希）后：

```
P(仍为 0) = (1 − 1/m)^(kn) ≈ e^(−kn/m)
P(为 1)   = 1 − e^(−kn/m)
```

**第 3 步** 查询一个不存在的元素，k 位恰好全为 1：

```
p ≈ (1 − e^(−kn/m))^k
```

对 k 求导令零，得最优值：

```
k* = (m/n) · ln2 ≈ 0.693 · (m/n)
p_min = (1/2)^k* = 0.6185^(m/n)
m/n = −ln(p) / (ln2)² ≈ 1.44 · log₂(1/p)
```

参数表（背下来就能用）：

| 目标误判率 p | 每元素比特 m/n | 最优 k | 100 万元素内存 |
| --- | --- | --- | --- |
| 10% | 4.79 | 3 | ≈ 0.6 MB |
| 1% | 9.59 | 7 | ≈ 1.2 MB |
| 0.1% | 14.38 | 10 | ≈ 1.8 MB |
| 0.01% | 19.17 | 13 | ≈ 2.4 MB |

注意跨度的性价比：误判率降 1000 倍，内存只涨 4 倍 —— 每多付 1.44 bit/元素，误判率降一个数量级。所以布隆过滤器常常被"过度配置"，反正便宜。

**实现技巧：双哈希。** 不必真的写 k 个哈希函数。Kirsch–Mitzenmacher 定理证明

```
g_i(x) = (h₁(x) + i · h₂(x)) mod m,  i = 0..k−1
```

的渐近误判率与 k 个独立哈希相同。每次只要算 2 个哈希，CPU 开销降 k/2 倍。本仓库实现就是这么做的。

## 6. 工程实践

| 系统 | 用法 | 收益 |
| --- | --- | --- |
| Chrome Safe Browsing | 本地存恶意 URL 前缀的布隆过滤器，命中后才联网校验 | 免去每次导航联网，且不泄露你访问了哪些正常站点 |
| RocksDB / LevelDB | 每个 SST 文件带一个过滤器 | 省掉绝大多数无意义磁盘 IO，缓解 LSM-tree 读放大 |
| HBase / Cassandra | 每个 HFile 一个过滤器 | 随机读从"扫多个文件"降到"只读一个" |
| Redis | `SETBIT`/`GETBIT` 手搓，或 RedisBloom 的 `BF.ADD` | 缓存穿透防护，拦住查不存在 key 的请求 |
| CDN / 爬虫 | URL 去重、已缓存资源判定 | 亿级规模下内存是硬约束 |

**上生产前必须知道的坑**

- 别用语言内置 `hash()`：Python 对字符串每进程加随机盐，重启后过滤器全废。用 MD5/SHA/blake2 这类稳定哈希。
- k 不是越大越好：超过最优值后误判率反而上升，还慢 k 倍。
- 容量必须事先估，m 定死改不了。宁可多留 50%。
- 分布式多节点各持一份会不一致；共享一份要注意并发写位的原子性（Redis `SETBIT` 原子，这也是它适合做布隆的原因）。
- 它不能枚举、不能精确计数。

## 7. 局限与替代方案

| 需求 | 该用什么 | 代价 |
| --- | --- | --- |
| 需要删除 | 计数布隆 / 布谷鸟过滤器 | 4× 内存 / 更可预测的误判 |
| 需要零误判 | 哈希表、B 树、Roaring Bitmap | 内存高一个数量级 |
| 需要取出元素 | 真正的集合结构 | 布隆从设计上不可枚举 |
| 容量持续增长且无法预估 | Scalable Bloom Filter（分层） | 层数越多误判越高，需按 0.5 递减分配 |
| 要压到 0.001% 以下还要省空间 | Ribbon Filter / XOR Filter | 实现复杂，但比布隆再省 30% |

演进脉络：**Bloom(1970) → Counting Bloom(可删) → Cuckoo Filter(可删、更省、更快) → Quotient / Ribbon Filter(RocksDB 现默认)**。这条线本身就是一部"榨干每一个比特"的历史，值得单独一期。

## 8. 自测题

先自己回答，再看答案。

<details>
<summary>1. 为什么布隆过滤器不可能出现假阴性？</summary>

位只会 0→1 单向变化。插入时命中的 k 位全被置 1，之后没有任何操作会清 0，所以再查必然全中。假阴性只可能来自删除操作或并发覆盖这类破坏单调性的实现 bug。
</details>

<details>
<summary>2. 100 万元素、0.1% 误判，需要多少内存和几个哈希？</summary>

m/n ≈ 14.38 bit，k = 10，总空间 ≈ 1.8 MB。对照：存 100 万个 20 字节字符串至少 20 MB，含哈希表开销通常 60~100 MB，省约 40 倍。
</details>

<details>
<summary>3. 把 k 从 7 调到 14（m、n 不变），误判率会降低吗？</summary>

不会，反而升高。k 增大使每个元素点亮更多位，位数组更快变满，这个效应压过"k 位全中更难"的效应。超过 k* 后误判率单调上升。
</details>

<details>
<summary>4. 为什么实现里常用双哈希而不是真写 7 个哈希函数？</summary>

Kirsch–Mitzenmacher 证明了 g_i = (h₁ + i·h₂) mod m 的渐近误判率与 k 个独立哈希相同。只需算 2 次哈希而非 k 次，CPU 开销大幅下降。
</details>

<details>
<summary>5. 缓存穿透防护里，为什么不能直接缓存空结果？</summary>

缓存空值也能防穿透，但攻击者可用大量互不相同的随机 key 打进来，每个都产生一条空值缓存，把缓存内存撑爆。布隆过滤器对任意多个不存在的 key 只占固定内存，这是它不可替代的地方。
</details>

[`bloom.py`](bloom.py) —— 零依赖，`bytearray` 按位存储，blake2b 双哈希，附带实时误判率估算与元素数反推。

```bash
python bloom.py          # 演示：内存、实测误判率、反推元素数
python test_bloom.py     # 9 项测试
```

实现里值得注意的四点：

1. `m`、`k` 由目标误判率自动推导，不手填魔法数字。
2. `h₂ | 1` 保证为奇数，避免 `h₂ = 0` 时退化成单哈希。
3. 维护 `_set_bits` 计数，可在运行时估算当前误判率而无需重扫位数组。
4. `estimate_count()` 用填充率反推 n：`n ≈ −(m/k)·ln(1 − X/m)`，误差 &lt; 2%。

## Lv1 · 基础（约 2 小时）· 从零实现 + 用数据验证公式

**目标**：让实测数据和你推的公式对上。

- [ ] 不用任何第三方库实现 `BloomFilter(n, p)`，支持 `add(x)` 与 `x in bf`，内部用 `bytearray` 按位存储（不是 `set`）。
- [ ] 写基准脚本：固定 `m/n = 10`，把 `k` 从 1 扫到 15，每个 k 用 10 万个随机串实测误判率。
- [ ] 把实测曲线和理论曲线 `(1−e^(−kn/m))^k` 画在同一张图上（matplotlib 或纯 SVG 都行）。
- [ ] 输出一张表：目标 p ∈ {10%, 1%, 0.1%} 时，实际内存、k、实测误判率各是多少。

**提示**：实测时探针串必须确实不在集合里，用 `f"__probe_{i}"` 这类前缀保证。

**你会学到**：为什么实测值总是比理论值略低（不完全独立的哈希、有限样本），以及位数组在填充率超过 ~70% 后误判率为何陡增。

## Lv2 · 进阶（约 4 小时）· 让它变成一个能用的工具

- [ ] 支持序列化：`save(path)` / `load(path)`，格式自定义，但必须带 magic + 版本号 + 参数头（`m`、`k`、`count`），保证跨版本可读。
- [ ] CLI 子命令：`init --n 1000000 --p 0.01`、`add <item>`、`check <item>`、`stats`、`bench`。
- [ ] 实现 `estimated_count()`：由填充率反推元素数 `n ≈ −(m/k)·ln(1 − X/m)`，验证误差 < 2%。
- [ ] 加 `--shard 8`：把过滤器拆成 8 个独立分片，对比误判率与单片差异。

**思考题**：分片会让误判率略微升高，为什么？（提示：每片的 m/k 比变了，且 n 的分配并不均匀 —— 用公式算一下 8 个片各自的 p 再合成总 p。）

**你会学到**：文件格式设计、参数校验、以及"分布式切片"对概率结构的隐性影响。

## Lv3 · 挑战（约 1 天）· 做一个可删除的版本，并打赢哈希表

二选一（都做更好）：

- [ ] **计数布隆过滤器**：每位 4 bit 计数器，插入 +1，查询看是否 >0，删除 −1；计数器饱和到 15 不回绕（超过就固定在 15，此时该位退化为不可删）。
- [ ] **布谷鸟过滤器**（Cuckoo Filter）：两个候选桶 + 指纹，支持删除且空间更省。

然后写一份**对比报告**：n = 100 万、p = 1% 下，比较「Python set / 计数布隆 / 布谷鸟」的：

| 指标 | 怎么测 |
| --- | --- |
| 内存 | `sys.getsizeof` + 递归统计，或 `tracemalloc` |
| 插入吞吐 | 插入 100 万条的总耗时（含预热） |
| 查询延迟 | 10 万次查询的 P50 / P99 |
| 误判率 | 10 万个探针实测 |

用真实数字说话，别写"更快""更省"这种词。

**Bonus**：给 [`bloom.py`](bloom.py) 提一个 PR，加上你实现的 `CountingBloomFilter` 及对应测试（注意：删除后必须**不产生假阴性**，这是验收关键）。

## 验收标准（提交前自查）

- [ ] 插入 10 万个元素后逐个查询，**零假阴性**（这条不过，其余都无意义）
- [ ] 实测误判率落在理论值的 0.5× ~ 2× 区间
- [ ] 内存占用 ≈ `n × (m/n) / 8` 字节，误差 ≤ 5%
- [ ] 有可复现的基准脚本，一条命令跑出全部数字
- [ ] README 里写清你踩到的坑（这比代码本身更有价值）

## 常见翻车点

| 症状 | 原因 |
| --- | --- |
| 出现假阴性 | 用了 `hash()`（进程间不稳定）→ 换个进程再查就挂了；或哈希算错了下标 |
| 实测误判率是理论值 10 倍 | k 或 m 算错，检查 `m = -n·ln p / (ln2)²` 里 `ln p` 是负数 |
| 探针误判率 ≈ 100% | 探针串本身被插进集合了 |
| 内存没省下来 | 用 `set` 存位置，而不是按位存 —— 一个 Python int 就 28 字节 |
